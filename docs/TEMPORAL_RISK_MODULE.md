# Temporal Risk Module

## Overview

The Temporal Risk Module estimates how strongly **recent and accumulated rainfall conditions are associated with elevated landslide risk** at a given observation location.

The module is one component of the overall NER Landslide Early Warning System.

The system separates landslide risk into multiple dimensions:

- **Spatial susceptibility** — how inherently susceptible a location is based on terrain and geographic characteristics.
- **Temporal risk** — whether recent rainfall conditions are activating or increasing the hazard signal.
- **Remote sensing / vision** — environmental or surface changes detected from imagery.
- **Risk fusion** — combines the different signals into a final risk assessment.

The Temporal Risk Module therefore answers:

> **"Given the rainfall conditions leading up to this observation, how elevated is the current temporal landslide signal?"**

It does **not** attempt to forecast future rainfall or claim that a landslide will definitely occur within a specified future time window.

# 1. Data Source

The module uses the processed dataset generated by the project's data pipeline:

```text
data/processed/ner_landslide_v1.csv
```

Dataset size:

```text

341 landslide samples
688 non-landslide samples
```

The dataset already contains rainfall features extracted from the IMD daily 0.25-degree rainfall data.

### Rainfall features

| Feature | Meaning |
|---|---|
| `rain_1d` | Rainfall accumulated over the most recent 1 day |
| `rain_3d` | Rainfall accumulated over the most recent 3 days |
| `rain_7d` | Rainfall accumulated over the most recent 7 days |
| `rain_15d` | Rainfall accumulated over the most recent 15 days |
| `rain_30d` | Rainfall accumulated over the most recent 30 days |
| `api` | Antecedent Precipitation Index |

The rainfall windows are strictly backward-looking and include rainfall leading up to the observation/event date.

No future rainfall observations are used by the temporal feature extraction.

---

# 2. Why Multiple Timescales?

Landslide triggering can depend on both recent rainfall intensity and accumulated wetness.

Looking only at rainfall on a single day can therefore miss important information.

For example:

```text
24-hour rainfall
       ↓
recent intensity

3-day rainfall
       ↓
short-term accumulation

7-day rainfall
       ↓
medium-term accumulation

30-day rainfall
       ↓
longer-term accumulation

API
       ↓
antecedent wetness
```

The module therefore considers rainfall across several temporal windows instead of treating rainfall as a single variable.

# 4. Temporal Feature Engineering

The feature engineering implementation is located at:

```text
src/temporal/features.py
```

The original rainfall variables are preserved, while additional indicators are derived to describe rainfall dynamics.

## 4.1 Recent Rainfall Concentration

The first indicator is:

```text
rain_1d / rain_7d
```

This measures the fraction of the recent week's rainfall that occurred in the most recent day.

A larger value indicates that a greater proportion of recent rainfall was concentrated in the latest 24 hours.

Example:

```text
rain_1d = 70 mm
rain_7d = 100 mm

rain_1d / rain_7d = 0.70
```

This indicates strong recent concentration.

---

## 4.2 Short-Term Accumulation Concentration

The module calculates:

```text
rain_3d / rain_30d
```

This measures how much of the 30-day rainfall accumulation occurred during the most recent 3 days.

It helps distinguish:

```text
gradually distributed rainfall
```

from:

```text
recent rainfall burst
```

---

## 4.3 7-Day / 30-Day Concentration

The module also calculates:

```text
rain_7d / rain_30d
```

This captures the proportion of longer-term rainfall that occurred relatively recently.

---

## 4.4 Rainfall Acceleration

Rainfall acceleration compares the recent daily rainfall rate with the longer-term daily rate.

Conceptually:

```text
recent 3-day daily rainfall rate
--------------------------------
recent 30-day daily rainfall rate
```

Implementation:

```text
(rain_3d / 3) / (rain_30d / 30)
```

Interpretation:

| Approximate value | Interpretation |
|---:|---|
| ~1 | Recent rainfall rate is similar to the 30-day rate |
| >1 | Recent rainfall rate is higher |
| >>1 | Strong recent rainfall intensification |

This provides a measure of whether rainfall has recently become more intense relative to the longer-term accumulation.

---

## 4.5 Daily Rainfall Intensities

The module derives:

```text
rain_3d / 3
rain_7d / 7
rain_30d / 30
```

These provide comparable daily rainfall rates across different accumulation windows.

---

## 4.6 API-Based Wetness Signal

The existing:

```text
api
```

feature is retained as an antecedent wetness indicator.

API incorporates rainfall history, allowing the model to consider rainfall memory rather than only the most recent rainfall event.

---

## 4.7 Log Transformations

Rainfall variables are strongly right-skewed, with extreme rainfall observations substantially larger than typical observations.

For this reason, log-transformed versions are used:

```text
log1p(rain_1d)
log1p(rain_3d)
log1p(rain_7d)
log1p(rain_15d)
log1p(rain_30d)
log1p(api)
```

These transformations reduce the influence of extreme values while preserving the ordering of rainfall intensity.

# 6. Model Selection

The final model is implemented in:

```text
src/temporal/model.py
```

## Final model

The module uses:

```text
StandardScaler
        ↓
Regularized Logistic Regression
```

The logistic regression model uses L2 regularization and class balancing.

### Why Logistic Regression?

The available dataset contains only 707 training samples.

Additionally, the current data is **event-oriented rather than a continuous time series**.

The data does not have a structure such as:

```text
Location A
  Day 1
  Day 2
  Day 3
  ...
  Day 365
```

Instead, observations contain backward-looking rainfall accumulation windows around individual observations/events.

Therefore, an LSTM/GRU-style sequence model would not be well justified by the current dataset.

A regularized logistic model provides:

- lower complexity,
- better interpretability,
- lower overfitting risk,
- reproducibility,
- a continuous risk score,
- interpretable model coefficients.

---

# 7. Overfitting Check

An initial gradient boosting model was tested.

The initial model produced:

```text
TRAIN ROC-AUC ≈ 0.994
TEST  ROC-AUC ≈ 0.574
```

This large generalization gap indicated substantial overfitting.

The model was therefore rejected.

The final implementation uses a much simpler regularized logistic regression model.

This produced substantially better held-out performance and a more defensible relationship between training and unseen spatial blocks.

---

# 8. Validation Strategy

The existing dataset already provides:

```text
train
validation
test
```

splits based on the project's spatial-block methodology.

The temporal model preserves these splits.

The data is **not randomly reshuffled** before evaluation.

This is important because random splitting could allow nearby observations to appear in both training and test data and produce overly optimistic results.

The final evaluation therefore uses the project's existing spatially separated held-out test set.

---

# 9. Final Model Performance

The final regularized logistic regression model achieved:

| Metric | Train | Validation | Test |
|---|---:|---:|---:|
| ROC-AUC | 0.587 | 0.649 | **0.730** |
| PR-AUC | 0.413 | 0.541 | **0.509** |
| Precision | 0.394 | 0.457 | **0.463** |
| Recall | 0.603 | 0.661 | **0.745** |
| F1 | 0.476 | 0.540 | **0.571** |

The most important overall discrimination metric is:

```text
TEST ROC-AUC = 0.730
```

The model also achieves:

```text
TEST RECALL = 0.745
```

which is useful for an early-warning application where missing a genuine hazardous event can be costly.

These results should be interpreted as evidence that rainfall-derived temporal features contain useful predictive signal in the held-out spatial test set.

# 10. Model Interpretation

The final logistic regression coefficients were:

| Feature | Coefficient |
|---|---:|
| `log_rain_1d` | +0.1693 |
| `log_rain_3d` | +0.1299 |
| `log_rain_7d` | -0.0008 |
| `log_api` | -0.0245 |
| `rain_3d_ratio_30d` | +0.0186 |
| `rainfall_acceleration` | +0.0187 |

The strongest positive coefficients are associated with recent rainfall intensity, particularly the 1-day and 3-day rainfall signals.

The model therefore places more emphasis on recent rainfall conditions after accounting for the other temporal features.

Individual coefficients should not be interpreted as causal effects. The model captures statistical associations in the available dataset.

# 11. Temporal Risk Score

The model probability output is converted into:

```text
temporal_risk
```

with a nominal range of:

```text
0–100
```

For example:

```text
temporal_risk = 52.8
```

means that the observation has a temporal risk score of 52.8 according to the trained model.

### Important interpretation

`temporal_risk` is a **model risk score**.

It must NOT be presented as:

```text
52.8% probability of landslide
```

because the model output has not been calibrated sufficiently to make that probabilistic claim.

The score is intended for relative risk ranking and fusion with other risk signals.

---

# 12. Operational Alert Threshold

For early warning, a continuous score can be converted into an operational alert.

Different thresholds were evaluated on the validation set.

Selected threshold:

```text
47
```

The threshold was selected using the validation set based on the precision/recall trade-off.

It was then frozen before evaluating the held-out test set.

At threshold 47:

```text
temporal_risk >= 47
        ↓
temporal_alert = True
```

Otherwise:

```text
temporal_alert = False
```

The threshold intentionally prioritizes recall because an early-warning system generally needs to reduce missed hazardous events even at the cost of additional false alarms.

---

# 13. Frozen Test Alert Performance

Applying the validation-selected threshold of 47 to the held-out test set produced:

```text
Actual landslide events: 51
Detected by alert:       44
Missed:                   7
```

Therefore:

```text
Recall = 44 / 51
       = 86.3%
```

The test set also contained false alerts, reflecting the deliberate recall-oriented operating point.

This is an operational alerting result and should be reported separately from the model's ROC-AUC.

# 15. Integration With Risk Engine

The Temporal Risk Module is designed as an independent component.

The Risk Engine can consume:

```text
temporal_risk
```

and optionally:

```text
temporal_alert
rainfall_24h
rainfall_72h
rainfall_7d
rainfall_30d
api
rainfall_acceleration
rainfall_concentration
```

The overall architecture is:

```text
                 LOCATION
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
     SPATIAL     TEMPORAL     VISION
      RISK         RISK         RISK
        │           │           │
        └───────────┼───────────┘
                    ▼
              RISK FUSION
                    │
                    ▼
              FINAL RISK
                    │
             ┌──────┴──────┐
             ▼             ▼
          WARNING      EXPLANATION
```

The temporal component therefore contributes one independent signal to the final risk engine.

# 17. Explainability

The temporal component provides interpretable rainfall indicators rather than only returning a model score.

Potential explanations include:

```text
Strong 72-hour accumulation
Recent rainfall intensity elevated
Elevated antecedent wetness
```

This allows the dashboard to explain:

> **WHY is the temporal risk elevated?**

instead of showing only:

```text
Temporal Risk = 52.8
```

This is particularly important for an early-warning system where users need actionable context.

---

# 18. Current Limitation: No Future Forecast

The current system does **not** perform 24-hour, 48-hour or 72-hour future rainfall forecasting.

The current temporal signal is based on rainfall observed up to the observation/event date.

Therefore, the correct interpretation is:

> **"Given recent rainfall conditions, how elevated is the current temporal landslide signal?"**

It should not be described as:

> "The model predicts a landslide will occur in the next 48 hours."

A future forecasting component could be added later if weather forecast data or continuous future-labelled rainfall sequences become available.

---

# 19. Current Limitation: Event-Based Dataset

The processed dataset is event-oriented rather than a continuous time series for every location.

Therefore, the current implementation does not use:

- LSTM
- GRU
- Transformer time-series models
- sequence-to-sequence forecasting

These approaches could be considered in a future version after constructing continuous location-level temporal sequences.

For the current prototype, feature engineering over multiple rainfall accumulation windows provides a more appropriate and explainable solution.

# 22. Summary

The Temporal Risk Module transforms multi-timescale rainfall history into an interpretable temporal hazard signal.

The pipeline is:

```text
IMD rainfall data
       ↓
1/3/7/15/30-day accumulation + API
       ↓
Temporal feature engineering
       ↓
Regularized Logistic Regression
       ↓
Temporal Risk Score (0–100)
       ↓
Operational alert threshold
       ↓
Temporal alert + rainfall drivers
       ↓
Risk Fusion Engine
```

The final model achieves:

```text
Test ROC-AUC = 0.730
Test PR-AUC  = 0.509
Test Recall  = 0.745
Test F1      = 0.571
```

Using the validation-selected operational threshold of 47:

```text
Held-out test alert recall = 86.3%
```

The module therefore provides the overall system with a dedicated, interpretable rainfall-based temporal signal that can be fused with spatial susceptibility and remote-sensing information.

---

## Key Design Principle

The Temporal Risk Module does not attempt to answer:

> **"Will a landslide definitely happen?"**

Instead, it answers:

> **"Are the current rainfall conditions showing an elevated temporal hazard signal?"**

This distinction allows the final system to combine multiple independent sources of evidence before issuing a landslide warning.
